### D-01 · Hold-mode for all mutating tools (conditional)
**Brief assumed:** Tally can hold a tool-call commit before the agent confirms.
**Reality:** in default `interactive` mode the agent speaks a transition phrase ("let me check…") and `tool.call` arrives *after* `reply.done` (Message sequence page). A spoken confirmation could therefore precede validation.
**Decision:** `add_item`, `remove_item`, `update_quantity`, `apply_modifier`, `confirm_order` are declared `execution_mode:"hold"` (agent stays silent until `tool.result`, which auto-triggers its reply). `get_order_state` stays `interactive`.
**Condition:** the Step 3 spike must produce a written PASS/FAIL (`docs/spike-g5.md`). Step 5 is blocked until it exists. See D-16.
**Spike outcome (2026-09-19):** the premise that hold mode keeps the agent silent before the first `tool.call` is TRUE (D-18), but hold mode as the gating architecture is NO-GO: the evidence Tally must judge against is not reliably delivered (D-16, D-19). D-01 stays in force as a *necessary* condition (the agent must not confirm before validation); it is not *sufficient*.
**Fail-closed:** no path allows a call because evidence is missing or late.

### D-02 · Barge-in is derived, not native
**Brief assumed:** a granular `barge_in` VAD event (`vad_events.type=barge_in`).
**Reality:** no such event. Available: `input.speech.started`, `input.speech.stopped`, `reply.done{status:"completed"|"interrupted"}`, `transcript.agent{interrupted:boolean}`. The server itself filters backchannels from real interruptions.
**Decision:** ingest derives a barge-in marker when **`input.speech.started` occurs while a reply is in flight (after `reply.started`, before `reply.done`) and that reply then ends with `reply.done.status==="interrupted"`**. Stored as `vad_events{type:'barge_in', derived:true, source_event_ids:[speech_started_id, reply_done_id]}`. If the reply completes normally, no marker (backchannel). Reaction time = `input.speech.started` → `reply.done(interrupted)` (client-observed, D-05).
**Spike evidence (2026-09-19, 2/2 captures with genuinely audible agent speech):** order is `transcript.agent{interrupted:true}` → `input.speech.started` → `reply.done{status:"interrupted"}`, all within ≈1 ms. The derivation holds; it must NOT depend on `transcript.agent` ordering, and must count only replies with **audible** audio (D-18). Detection fired ≈2.5–3.0 s after our correction audio began, coinciding with the end of the agent's sentence, so mid-sentence truncation was not observed (N=2, synthetic). Backchannel ("uh-huh" over speech): 0/2 interrupted, but it becomes a new user turn afterwards. Fixtures: `fixtures/aai-events/barge_in_speech-*.jsonl`, `backchannel_speech-*.jsonl`.
**Caveat (original):** the interrupted-turn event ordering is not documented; the Step 3 spike captures a real fixture and the derivation is pinned to it. Pitch wording: "derived from AssemblyAI's interruption events".

### D-03 · No transcript confidence; text-instability is the proxy
**Brief assumed:** `utterances.confidence` from partial/final transcripts.
**Reality:** `transcript.user.delta` and `transcript.user` carry `text` (and `item_id`) only; no confidence.
**Decision:** `utterances.confidence` is NULLABLE and unused for verdicts. Confidence proxy = **text-instability scoring**: (a) partial-vs-final divergence (edit distance between last delta and final), (b) delta churn count for the entity spans, (c) ambiguity flags from the extractor (homophones `to/two`, `for/four`). Unstable or ambiguous evidence ⇒ `HOLD` (fail closed), never ALLOW.
**Correction from the spike (2026-09-19):** the stored session timeline (`GET /v1/sessions/{id}`) carries a `user_confidence` per turn (observed `1`, uninformative in this sample), but it is post-hoc only and absent from the live stream, so the decision stands for live gating.
**Update (spike A, 2026-09-20):** the independent stream (D-04) DOES provide per-word `confidence` on every `Turn` (0.63–0.89 on the correction finals). Confidence-driven holds (low-confidence words inside a quantity/item span) will therefore use the independent stream's word confidences; text-instability remains a complement, and the stored-timeline `user_confidence` is constant 1.0 (uninformative).
**Fold-in:** false-positive rate (metric 8) is used to tune instability thresholds; auto-tuning stays an extension (brief §13).

### D-04 · Independent Tally-owned STT stream: REVERSED, now required before Step 5
**Original decision (superseded):** second STT stream for confidence deferred until after Step 12; schema not confirmed; not scoped.
**Reversal (owner-approved 2026-09-20):** the second stream is now **required before Step 5** and is the **primary correction-evidence source** for gating. It runs on the same raw input audio Tally already records/sends, over its own connection (`wss://streaming.assemblyai.com/v3/ws`, `speech_model=universal-3-5-pro`), so it is independent of the Voice Agent session's hold state and of the agent's LLM.
**Reasoning:** the Step 3 spike found a live-stream evidence gap: in **7 of 8** late-correction / during-hold runs the correction's `transcript.user` never reached the live stream, although AssemblyAI's own stored timeline had it (`docs/spike-g5.md`). Speech-activity signals were blind in 5 of 12 correction runs and a buffer window cannot wait for evidence that never arrives. The purpose therefore changes from "confidence" to **evidence availability**; per-word confidence is a bonus. Text-instability scoring (D-03) remains the fallback/complement.
**Cost/complexity accepted:** about $0.45/h extra, one more connection, and a second transcript to reconcile with the agent stream (the agent stream stays the record of what the *agent* heard; the independent stream is the record of what the *customer said*).
**Conditions:** (1) **Spike A is blocking**: Step 5 may not begin until it confirms the stream keeps delivering transcripts in real time while the primary session is in a hold state, on the scenarios that failed (late 400/900/1500 ms, during-hold, silent-reply barge-in). (2) Boundary: the STT client lives in its own workspace (`/stt`), not in `/reliability`; it is input-audio-only and has no path to voice output (ARCHITECTURE §4.1 unchanged). (3) Secrets: same server-side key rule (SECURITY §2).
**Outcome (2026-09-20, `docs/spike-a.md`): spike A PASSED. The independent stream closed the evidence gap in this sample.** 21 hold-mode sessions, 18 corrections: the independent stream delivered **18/18** (final text correct, with the correction cue, 18/18) against **7/18** on the Voice Agent live stream, including all 11 corrections the agent had committed stale and the live stream lost. It kept delivering *during* a hold (10 turn updates inside the hold in `correction_during_hold`, where the agent stream produced 0 speech events and 0 transcripts, 3/3). Its `SpeechStarted` fired in 15/15 late/hold/barge runs at 0.52–0.75 s lag (the agent's: 1.29–2.20 s, and never during hold). Its first final beat the agent's first `tool.call` in 21/21 runs, so the uncorrected path pays **no** latency. Measured worst-case wait for the final after `tool.call`: **3470 ms** ⇒ recommended `EVIDENCE_WAIT_MAX_MS=4000`, fail closed on expiry. Caveats: N=3, synthetic clean speech, one speaker; real-world accuracy unproven. Step 5 is unblocked by this spike but has **not started**, pending owner review.

### D-05 · Client-stamped timestamps and audio offsets
**Reality (CORRECTED by the spike, 2026-09-19):** the docs list no timestamps, but **every inbound event carries a server `timestamp` field (Unix seconds, float)**, verified on `session.ready`, `reply.*`, `transcript.*`, `input.speech.*` and `tool.call`. Step 4 must store it (`events_raw`, `utterances`) and prefer it for ordering and latency where available; client stamps remain for provenance and for outbound events. The original claim was wrong: "events carry no server timestamps (only `transcript.agent.delta` `start_ms/end_ms`)".
**Decision:** every inbound event gets a monotonic `t_ms` and `wall_ms` on receipt; `audio_offset_ms` = bytes of input PCM sent ÷ 48 (24 kHz, 16-bit mono). Provenance = `(event id, audio_offset_ms)`. All latency metrics are labelled **client-observed**.

### D-06 · "Claimed / evidence / actual" redefined
**Brief assumed:** a tool-call result callback exposing the agent's claimed result separately from the actual result.
**Reality:** `tool.call` = `{call_id, name, arguments}` only; we author `tool.result`.
**Decision:** `claimed_result_json = {arguments, spoken_text}` (spoken text from later `transcript.agent`); **evidence** = deterministic extraction from `transcript.user`; **actual** = DB diff produced by the committer and re-read via the read-only connection. Drift is judged on spoken text vs actual state; the agent's words are never evidence for ALLOW (rule 3). "Silent tool lie" = handler-returned result ≠ independently re-read diff (`TOOL_RESULT_LIE`).

### D-07 · Two-tier replay
**Reality:** the managed LLM cannot be seeded; user audio is not echoed by the server; input must be sent ≤ real time.
**Decision:** *Evidence tier* (stored events through current gating code) = **deterministic PASS/FAIL**, used for compare view and promotion gate. *Audio tier* (live audio + managed agent) = **"k/3 passed"**, PASS requires 3/3, **never labelled deterministic**. Brief §19 acceptance criterion amended accordingly (PRD Part D). Raw input PCM is recorded by Tally itself for replay.

### D-08 · HTTP tools and bring-your-own-LLM banned
Both exist in the platform. HTTP tools execute server-side at AssemblyAI (bypassing gated client path; rule 8). BYO-LLM docs don't specify tool-call interception. Only client-side tools are used.

### D-09 · Tally supplies repair instructions only; no path to voice output
**Brief tension:** §5 "Tally must not control voice output" vs §6 "inject a repair prompt".
**Decision:** Tally returns a typed `RepairInstruction` data value. Only Plane 1's `RepairAdapter` converts it into the `tool.result` payload and `reply.create{instructions}`. `/reliability` and `/contract` may not import the socket/`ws`/network modules or reference output-audio types or `reply.*`/`tool.result`/`input.audio` senders. Enforced by `npm run check:boundaries` (ARCHITECTURE §4.1).

### D-16 · Hold-mode ordering risk and buffer window (conditional)
**Risk:** in hold mode the docs say `transcript.user` "flushes after hold ends" and user speech during a hold "only adds context". A correction spoken after the model emits `tool.call` (scenario B) might not reach Tally before Tally must send `tool.result`.
**Mitigations already designed:** `input.speech.started/stopped` still fire → treated as pending-evidence signals (`PENDING_EVIDENCE` HOLD); bounded `SETTLE_MS`.
**Blocking gate:** the Step 3 spike measures, on real captured events, (1) whether `tool.call` precedes/follows `transcript.user` finalisation, (2) whether speech-start/stop events fire during hold, (3) how late a correction's `transcript.user` arrives relative to `tool.call`, (4) the audible silence length in hold mode. Report: `docs/spike-g5.md` with explicit PASS/FAIL.
**If corrections routinely arrive after the point where `tool.result` would be sent:** a `GATE_BUFFER_MS` window is added to gating logic **before Step 5 starts** and recorded here; if even that is insufficient, fallback is `tool.result` carrying a HELD repair instruction (still fail closed). No "allow after timeout" path is ever permitted.
**Recorded outcome (2026-09-19, real API, 20 valid sessions; full write-up `docs/spike-g5.md`): NO-GO for hold-mode gating as designed, and a buffer window alone does not fix it.**
- Hold works as a *silence* mechanism: before the first `tool.call` the server streams `reply.started` plus silence frames only (RMS≈0); the agent speaks only after tool results (D-18).
- It fails as an *evidence* mechanism: in the 8 late-correction / during-hold runs the correction's `transcript.user` reached the live stream in **1 of 8** (7 of 8: never, though the server timeline recorded it and the LLM later used it). Across all 12 correction runs the first `tool.call` carried the stale quantity in **9 of 12**, and **6 of 12 ended stale** (the agent even *said* "two burgers" to a customer who said three).
- `input.speech.started` is not a dependable early warning: 115–980 ms before `tool.call` in five late runs, **1.0–1.2 s after** it in the silent-reply barge runs, and **it did not fire at all during a 2.5 s hold** (2/2).
- **Buffer window: NOT adopted.** It waits for evidence that, in 9 of 12 runs, never arrives on the live stream (observed for 4–17 s); a signal-only buffer would need more than 3 s (VAD lag p95 ≈ 3.0 s); and treating "no evidence" as a hold would hold nearly every late-correction call. `GATE_BUFFER_MS` stays 0 pending D-19.
- Fail-closed is unaffected: nothing is allowed on missing evidence. The gap is that the live stream cannot supply the evidence.
- Caveats: N=2 per scenario, synthetic SAPI speech, client-observed timings. This is a feasibility finding, not a failure-rate estimate. Run 1 (16 sessions) was contaminated by a harness bug (greeting collision, no audio energy) and is excluded (`fixtures/aai-events/run1-greeting-collision/`).

### D-17 · One order line per item; DB-level rule-8 enforcement (implementation decisions, Step 1–2)
- **One line per `item_id`.** Modifiers apply to the whole line, so "two burgers, one without onions" is not representable; `add_item` on an item already on the order is rejected (`ALREADY_IN_ORDER`, use `update_quantity`/`apply_modifier`). Chosen because ambiguity about add-vs-set quantity is exactly the failure Tally exists to catch; representing split lines is a post-hackathon extension. Exclusive modifier groups (flavor, size, ice) replace rather than stack.
- **Rule 8 is enforced in the database, not just by convention.** Triggers require every `orders` insert/update to carry a *new* `last_validation_event_id` that already has a paired `audit_events` row; orders cannot be deleted; `events_raw`/`audit_events` are append-only; case snapshots and config content are immutable. A test shows that even a full-privilege handle cannot bypass them. The application writer (`reliability/src/committer.ts`, class `Store`) never exposes its handle and accepts only a branded `AllowDecision`, which only the gate may mint (`check:boundaries` rules `single-write-path`, `admin-handle-db-only`, `single-allow-path`).
- **Honest limit:** these guards stop accidental and structural violations; they do not defend against malicious code already running inside the Tally process (which could forge an audit row). Out of scope for the demo (SECURITY §6).

### D-18 · `reply.started` is not speech; hold mode streams silence padding (spike finding)
In hold mode, between the end of the user's turn and the `tool.call` (about 1.5 s), the server sends `reply.started` followed by `reply.audio` frames of silence. Judging "the agent spoke" (H1) or "a reply is in flight" (D-02) from `reply.started` alone is wrong; it produced a false H1 FAIL in the first analysis. Ingest and analysis must use audio energy (per-chunk RMS, threshold 100 on PCM16) to tell speech from padding. Tool calls are issued one at a time, each inside its own silent reply, so a multi-item order produces several holds. Confirmed by transcribing the stereo recording of one session.

### D-19 · Live transcript is not a reliable evidence source under hold mode (DECIDED 2026-09-20)
Finding F2 (`docs/spike-g5.md`): speech that overlaps a hold is recorded server-side but mostly not delivered as live `transcript.user` events (7 of 8 late/hold runs). **Owner decision:**
- **A. APPROVED, primary.** Tally-owned independent STT stream on the same raw audio is the correction-evidence source for gating (D-04 reversed). **Spike A is blocking before Step 5.**
- **B. APPROVED as a diagnostic only.** Interactive-mode comparison, run alongside A, whose sole purpose is to learn whether the evidence gap is specific to hold mode or present in the base protocol. **B's design (the agent speaks before validation) must not become the gating design**, whatever it shows. D-01 stays.
- **C. APPROVED, permanent safety net layered on top of A**, not a replacement: post-hoc reconciliation of the live/independent transcripts against AssemblyAI's stored session timeline, using its `user_confidence` field. Detection, not prevention; feeds RECORD FAILURE.
- **D. REJECTED.** Speech-activity signals plus a buffer were blind in 5 of 12 correction runs.
**Outcome of spike A / B (2026-09-20, `docs/spike-a.md`):**
- **A: PASS** (see D-04). **Adopted as the primary correction-evidence source.**
- **B (diagnostic): the evidence gap is specific to hold mode in this sample.** Interactive mode delivered the correction live 12/12 (hold: 7/18) and the agent ended with the correct quantity 12/12 (hold: 12/18 correct, 6 stale). Both modes made a premature first call (9/12 interactive, 11/18 hold), so an independent check is needed regardless. **B's approach was not adopted and does not change D-01**; per the owner's instruction it stays a diagnostic. An unexpected observation (no audible agent speech before the first `tool.call` in interactive mode either, 12/12) is recorded but is a small, prompt-dependent sample and is not a design signal.
- **C: implemented and validated on 33 real sessions** as a permanent safety net: `reliability/src/reconcile.ts` (pure) + `stt/src/timeline.ts` (read-only fetch). It flags exactly the 11 stale-first-call sessions and nothing else (0 false positives after fixing a merge-matching bug that had produced 6). **Finding: stored `user_confidence` is constant 1.0 across all 53 stored turns, so it carries no information in this sample.** It is wired (`LOW_TIMELINE_CONFIDENCE`) as an optional cross-check only; confidence-driven holds will use the independent stream's per-word confidences instead (D-03 update below).
- **D: rejected** (unchanged).

### D-20 · Duplicate tool calls (observed `add_item(coke)` repeated in every clean run)
**Observation (real API, `fixtures/aai-events*/clean_order-*.jsonl`):** in **5 of 5** valid clean-scenario runs the agent, after `add_item(burger ×2)` and `add_item(coke ×1)` had both succeeded, issued a **third call, a duplicate `add_item(coke ×1)`** with a new `call_id`. In 1 of the 5 the duplicate also carried a modifier the customer never said (`size_large`), a real unsupported-claim example for Step 14. The stub returned an error, and the agent then apologised to the customer ("I already have a Coke on the order…"), confusing an otherwise correct order.
**Did the existing logic dedupe identical calls? Partly.** There is no gate yet (Step 5 not started). In the commit path: `add_item` on an item already on the order was rejected (`ALREADY_IN_ORDER`) so the order never double-committed (verified: totals unchanged in the captures), but (a) an *exact repeat* of committed state was reported as a conflict, which made the agent apologise; (b) no-op `update_quantity` / `apply_modifier` calls would have committed an audit-paired no-op; (c) replaying the same `call_id` hit the `UNIQUE(session_id, aai_call_id)` constraint and surfaced as a generic `COMMIT_FAILED`.
**Decision and change (done now, tested):**
1. **`NO_CHANGE`** (`reliability/src/order.ts`): an exact repeat of what is already committed (same item + quantity + modifier set in any order; `update_quantity` to the current value; `apply_modifier` already applied) is a harmless no-op. Nothing is written: no `tool_calls` row, no audit row, order hash unchanged.
2. **`add_item` on an existing item with different args stays a conflict** (`ALREADY_IN_ORDER`): that is a real disagreement (e.g. the unrequested `size_large`) and remains for the gate to judge (`MODIFIER_MISMATCH` / `UNSUPPORTED_CLAIM`).
3. **Call-id idempotency** (`reliability/src/committer.ts`): replaying an already-committed `aai_call_id` returns the recorded outcome (`idempotent: true`) and writes nothing.
4. **Plane 1 wire result** (`agent/src/repair-adapter.ts`, `noopResult`): `NO_CHANGE` becomes `{status:"NOOP", message:"…Nothing changed and nothing went wrong. Do not apologise…"}` so the agent does not confuse the customer.
5. **Step 5 requirements (recorded, not yet built):** the gate must (a) treat `NO_CHANGE` as a non-conflict, non-committing outcome, (b) still judge a *non-identical* duplicate (different modifier/quantity) against evidence, and (c) never let deduplication turn a HOLD into an ALLOW (dedupe applies only to calls that are already valid and equal to committed state).
**Tests:** 5 new cases in `reliability/test/committer.test.ts` (idempotent replay; the clean-scenario duplicate is `NO_CHANGE` and writes nothing; different-args duplicate stays `ALREADY_IN_ORDER`; no-op update/modifier; modifier-order insensitivity).

### D-21 · Validation status of the independent-evidence design, and a required real-speech pass (owner decision, 2026-09-20)
Approved: Step 5 gate judges against the independent stream (D-04), waits up to `EVIDENCE_WAIT_MAX_MS=4000` **only while someone is speaking**, holds on expiry / dead stream / low-confidence quantity-or-item word, and runs option C after every call.
**Validation status, stated plainly:** spike A (`docs/spike-a.md`) used **synthetic speech (Windows SAPI), clean audio, a single speaker, n = 3 per scenario (2 for B)**. Its "18/18" and the 3470 ms worst-case wait are feasibility measurements, not accuracy or latency guarantees. `EVIDENCE_WAIT_MAX_MS` and `MIN_WORD_CONFIDENCE` are provisional.
**Required:** one **real-speech validation pass** (TESTING.md §11: human speakers, real mic and room noise, at least one imperfect and one overlapping correction) **before the final demo lock**. It is a separate gate from Step 4's unit/integration work and from Step 5's test suite, and its results (including failures) are committed to `docs/real-speech-validation.md`. Until then no accuracy claim about the independent stream, the local speech check or the false-hold rate may appear in demo material.

### D-22 · Confirm-time reconciliation of the order against the customer's evidence (implemented 2026-09-20)
**Gap found by direct measurement:** a gate that judges each call at the moment it arrives cannot see a correction the customer begins *after* the call. In the 3 `correction_during_hold` captures the customer started "No, wait, make it 3" 145–199 ms after the agent's `add_item(burger, 2)`. At decision time nobody was speaking and the customer had said only "two burgers", so ALLOW was correct then. If the agent then never applied the correction (as happened in 2 of the 3 real runs), the order would stay at 2 while the customer said 3.
**Decision:** `confirm_order` (the last checkpoint before the kitchen) is held unless the committed order equals the evidenced intent: every evidenced item present with the same quantity and modifier set, nothing on the order the customer never asked for, removed items gone (`reliability/src/judge.ts` `reconcileOrderWithEvidence`). Codes: `QTY_MISMATCH`, `ITEM_MISMATCH`, `REMOVAL_MISMATCH`, `MODIFIER_MISMATCH`, `UNSUPPORTED_CLAIM`; ambiguity or low word confidence => `UNVALIDATABLE`. The hold carries a scoped repair instruction like any other.

### D-27 · Step 6 targeted repair (2026-09-20): design, and what is and is not validated
**Design (all in `/reliability` + `/contract`; the agent adapter only translates):**
- **Scope key** = the disputed `item_id`, or `'order'` (confirm_order / no item). `ITEM_MISMATCH` also records `alt_scope` = the item the customer actually asked for, so a valid call on either item closes the dispute.
- **Attempts** = pending unresolved asks on the scope + 1. Asks 1 and 2 are the scoped question (PRD §B.9, N=2). The next unresolved hold on that scope **escalates**: earlier asks are marked `escalated`, the instruction becomes a hand-off (`escalationText`, not a question), and further holds on the scope answer "escalated" without writing more rows. Repeats of the same call id (idempotent replays) never advance the counter.
- **Only real disagreements are repaired.** Agent misuse (`projection_error`) creates no repair row and asks the customer nothing.
- **Resolution rule:** a repair is resolved ONLY by a call that has just passed every gate check: inside the committing transaction (`resolves_scopes`), or by a validated NOOP repeat. The customer's "yes" is evidence for the gate, never a resolution by itself; the re-issued call must still match it.
- **Escalation is not a lock-out.** The gate's safety never depended on repair state: if later evidence and a later call agree, committing is still correct. The escalated row keeps `outcome=escalated` (the honest history) and gets `resolved_at`; the next dispute on that item starts at attempt 1. (Alternative rejected: refuse valid calls after escalation, which would trade a correct order for a rule.)
- **Instruction-only preserved:** Tally emits data (`RepairInstruction` with `escalated`); `heldResult` in Plane 1 renders it; an escalated result tells the agent not to re-ask or re-call for that item and to continue the rest of the order. In hold mode the `tool.result` itself triggers the agent's reply, so no `reply.create` is sent.
- A `repair` event (asked / escalated / resolved) is emitted for the timeline and call log.
**Found while building:** the removal template produced "keep 1 on the classic burger?" (an internal evidence string leaking into speech). Fixed to a real question.
**Validation status: NOT VALIDATED.** Automated tests (446 total) prove Tally's side: what is asked, counted, escalated, persisted, resolved, and that nothing else is touched. They do NOT prove the real agent speaks the HELD instruction well. Two independent conditions must BOTH pass before Step 6 is demo-ready, and neither substitutes for the other:
1. the real-speech pass (evidence/extraction accuracy on real phrasing, D-26), not yet scheduled;
2. a live-mic session exercising the real repair loop and barge-in over the agent, possible only with Step 11's dashboard mic page (a recorded WAV cannot answer the re-ask).
**Known limits:** repair wording is templated and untested on real customers; unresolved repairs at hangup remain `pending` (Step 7 turns them into cases); `SPOKEN_STATE_DRIFT`-triggered repairs (post-commit, from the agent's own speech) are Step 10.

### D-30 · Step 8 replay: what PASS means, the one replay-only write, audio-tier accounting (2026-09-20)
- **What a replay asks:** "does the CURRENT build still handle this recorded call correctly?" Evidence tier, three cases: (1) *expected state exists* (repair resolved): the recorded call is projected onto `order_before`; if the resulting line for its item equals the validated line the call was CORRECT and the gate should ALLOW it, otherwise the gate must HOLD it and leave the order untouched. This is what lets a later improvement to a false hold show up as a change, and a regression that lets a bad call through show up as `SAFETY_REGRESSION`. (2) *evidence-unavailable holds* (`stream_down`, `evidence_timeout`, `no_evidence`): the hold was right whatever the customer confirmed afterwards, so the same stored evidence must keep producing HOLD (otherwise an outage case would fail forever). (3) *no expected state*: only the fail-closed claim, a held call stays held.
- **Not compared:** the repair wording or attempt number (those depend on prior repair history, which a single-call snapshot does not carry) and the agent's speech (rule 3). `code_changed` is reported in the diff but is not a failure: a different HOLD code is still a hold.
- **Determinism, precisely:** virtual clock, no randomness, no wall-clock in `diff_json` (validation ids and timestamps are excluded; `waited_ms` comes from the virtual clock). Same snapshot + same gating code => same bytes. Any change to the gate/extractor/evidence code is exactly what is being tested, so a change in result means the build changed.
- **The one replay-only write (flagged for review):** an evidence replay must put a throwaway order into the state the case saw. `Store.seedReplayOrder` does that and is hard-guarded: it throws for any session that is not `mode='replay'`, writes the same audit pairing as every order change, and only ever runs in a temp database that is deleted afterwards. It is the only order write that is not a gate ALLOW; rule 8's boundary script still passes, and a test proves it refuses live and demo sessions. Alternative rejected: storing every prior allowed call with its evidence in every snapshot (large, and replays would then depend on replaying history rather than the one call).
- **Audio tier accounting:** the case audio is the WHOLE call's input, so the replayed agent may ask its questions at different moments than the original, and the recording cannot answer them (the same limit as the real-speech pass). The judged claim is therefore narrow and honest: after the stored audio plays, does the final order (from the database) equal the expected state? k=3, all must pass, reported "k/3 passed". Each attempt is its own `mode=replay` session with its own recording, and a replay never creates cases. Audio tier needs an expected state; a case without one is refused (409), not guessed at.
- **Time-to-replay** is stored per run (`replay_runs.duration_ms`) and reported per tier, never blended: evidence is milliseconds, audio is k x clip length plus settle time (default 8 s tail).
- **Validation status:** the evidence tier is fully tested. The audio tier is validated against MOCK Voice Agent and STT servers only. It has not been run against the real managed agent because that needs a real resolved case (a real hold followed by a re-validated commit), which needs the live-mic session. No repeatability claim is made about the real agent until it has.


### D-31 · Step 9 promotion gate: what it guarantees, and what it inherits (2026-09-20)
**Plain statement of the guarantee (owner request).** The promotion gate inherits the current validation status of the regression suite it depends on. That suite is operator-accepted cases built from **synthetic and captured phrasing only**. The real-speech validation pass (D-26) has not run, and no live-agent / live-mic session has exercised the repair loop or the audio tier against the real managed agent (D-27, D-30). Therefore a promotion PASS means exactly one thing: *none of the known, accepted failure cases regressed under this candidate's gating parameters (and, when the audio tier ran, under its prompt, on mock or recorded audio).* It does NOT mean the candidate is reliable on real callers, and any claim beyond that is overstated. The notice is attached programmatically to every suite report and promotion response.
**What the gate does**
- `runSuite` = manual "run all cases": every `regression`-tagged case, evidence tier, candidate's gating parameters, mandatory 100%. Any failing case blocks; the report names it. The audio tier (k=3) is opt-in per run and, when run, must also pass for every case.
- `activate` (data layer) requires a suite run for exactly that version that PASSED, covered exactly the current regression set (else STALE), and is unused (else CONSUMED); the config's hashes must verify. A run cannot be reused, and nothing changes on any failure.
- **Empty suite:** passes, labelled vacuous. That is honest but weak: the first configs are promoted with no regression evidence at all. Accepting cases (operator, D-29) is what gives the gate teeth.
**Decisions taken here, for your review**
1. **A changed prompt or tool schema requires the audio tier (my addition, not in the request).** The evidence tier replays stored events through the GATING code, so it cannot see a prompt change: a prompt-only candidate would "pass" while measuring nothing about the change. So when the prompt/schema differs from the parent and regression cases exist, an evidence-only suite is BLOCKED (`AUDIO_TIER_REQUIRED`). The cost is real: the audio tier is real time x k per case against the live agent, and is unproven on the real agent (D-30). If you would rather allow prompt promotions on evidence alone, it is one line in `runSuite`, but the result would then be quoting a pass that says nothing about the prompt.
2. **The tool schema is not configurable.** It is always the contract's; hold-mode for mutating tools is a safety invariant (D-01), so a config cannot weaken it. It is still hashed and versioned.
3. **`turn_detection` is not accepted** (stored `{}`): the agent session has no such option today; recording an unapplied setting would be a false record.
4. **Gating parameters are validated to ranges**, but a candidate CAN lower `minWordConfidence` to 0. That is a legitimate tuning knob, and exactly what the regression suite exists to catch (the test config that does this is blocked, naming the case). With no case protecting it, nothing would stop it.
5. **Rollback needs no suite**: the parent was active before, its hashes are re-verified, and speed matters more than ceremony when reverting. It is recorded in `config_events`.
6. **Only the committer handle writes `promoted`**, enforced by the existing boundary rule (single write path) and the `activate` checks; there is no DB trigger forbidding a raw `UPDATE configs SET promoted` from that same handle. Adding one would need the event and the flag flip ordered inside one trigger-visible transaction; deferred as low value inside a single-writer process.
6b. **Known gap, stated plainly:** the `promoted` flag is protected by application-level enforcement only (single committer handle, the `activate` checks, the boundary script). There is **no database-level backstop**, and this is **not equivalent to a trigger**: a bug or a rogue write from inside the committer process could flip the flag without a passing suite run. It is a known gap, accepted for hackathon scope, and it is NOT already covered.
7. **New sessions run the active config.** Promotion therefore changes real behaviour (prompt and gating parameters for the next call); calls already in progress are unaffected.
**Not validated:** everything above is proven on synthetic/captured cases and mock servers. The suite's strength grows only as real cases are accepted.


### D-32 · Step 10: repairs triggered by the agent's own spoken drift (2026-09-20)
**What it is.** After the agent speaks, its words are compared with the committed order (rule 3: speech is never ground truth). A wrong quantity, an item not on the order, or a wrong total becomes a scoped repair whose correction states the TRUE value, is stored (claim row, repair row, case), and is spoken by the agent via a one-shot `reply.create` sent by Plane 1.
**Design decisions (for review)**
1. **Detection is after the fact, so the wrong words WERE heard.** In hold mode the agent is silent until `tool.result`, so what Tally controls is what the agent is TOLD; what it then says is free. Spoken drift can only be corrected, not prevented. This is the honest limit of the whole approach.
2. **`tool_calls` row with tool `agent_speech`.** The schema requires every repair and case to reference a tool call. A spoken claim is recorded as one (status `conflict`, mode `interactive`, args = the text and the finding) rather than loosening the schema, so cases, replay, the tagger and the audit trail work unchanged.
3. **Guards, deliberately conservative ("a wrong correction is worse than a miss"):** if the order changed while the reply was being spoken, the statement may have been true when said, so nothing is raised; interrupted replies are partial and skipped; questions and offers are ignored. Each skip is audited.
4. **Bounded, no loop:** per scope, 2 corrections, then one hand-off, then silence. The correction reply is itself checked, so a right restatement resolves it. Drift accounting is separate from hold accounting (`kind` filter in the store), so a hold dispute and a drift on the same item cannot resolve or exhaust each other (tested).
5. **Resolution needs a CORRECT statement.** Silence about the item, or another wrong statement, does not resolve. The case's expected state is the committed order, which the gate validated (the agent's words are not the evidence).
6. **Delivery is one-shot `reply.create`, never a tool result** (there is no tool call in flight to answer). It is queued behind any reply in flight. The instruction says what is true, that nothing changed, and not to call a tool.
7. **Total everywhere is recomputed.** Results to the agent recompute from the lines; the gate's read-back compares stored vs recomputed (`TOTAL_MISMATCH`). The stored total is never repeated as-is.
8. **A drift case replays through the current drift check** (`drift_detection`), deterministic like the rest of the evidence tier. It has no expected-state comparison to make; the only claim is "the current build still detects this".
**Limits, stated plainly**
- The drift check covers quantities, "item not on order", and the total. It does NOT check modifiers, pickup time, or item names the agent gets wrong, and it is claim extraction on text: an unusual phrasing ("a couple of burgers", "the usual") is missed. A miss is silent (no correction), which fails toward the customer hearing the wrong thing, not toward a wrong order: the order itself is only ever changed through the gate.
- Whether the REAL agent follows the `reply.create` correction is unmeasured (mock server only). It could ignore it, over-apologise, or re-open the topic. That needs the live-mic session.
- A correction takes a full extra turn; on a slow reply the customer may already have moved on. Nothing here interrupts the customer.
- Reply/transcript ordering on the real API (transcript before or after `reply.done`) is handled both ways by queueing, but only the documented order was exercised.


### D-33 · Dashboard technology: a deviation from the PRD (2026-09-21)
The PRD said Vite + React + Playwright. Built instead: plain TypeScript, pure reducer + string views, bundled with esbuild (already a transitive dependency), served by the API server itself, tested with vitest + jsdom. **Why:** fewer moving parts and no second dev server (one origin means no CORS and a strict CSP), everything escaped in one place, and the live state is a pure function of the event stream, which is the property worth testing. **What it costs:** no component library, hand-written views, and **jsdom is not a browser**: layout, real audio capture/playback and real-browser quirks are untested (a Playwright/real-Chrome pass is the missing check). **How to reverse:** the views are pure functions of data, so a React layer could replace `views.ts` without touching the reducer or the API.

### D-34 · Deterministic demo mode is scripted, and says so (2026-09-21)
The PRD described demo mode as prerecorded audio through a REAL AssemblyAI session. A real managed agent cannot produce identical output twice, so "identical on repeat runs" and "real session" contradict each other. Decision (owner asked for identical output): **the Voice Agent and the "independent" transcripts are scripted in-process servers on loopback; everything else is the real pipeline** (recorder, local speech check, ingest, tracker, gate, committer, drift, repair, cases, tagger, replay, promotion, metrics, SQLite) fed by real prerecorded audio. Consequences, all stated on screen and in DEMO.md: the banner "DETERMINISTIC DEMO: … scripted agent" is always visible; results carry `scripted: {agent, transcripts}`; audio-tier replay in the demo is the scripted agent (3/3 there proves the runner, not the real agent); cases from demo runs are `origin_mode=demo`. The live mode (real agent, your microphone) is unchanged and non-deterministic. **The seed does not fabricate data:** it plays the scenarios, then makes one operator acceptance (audit-logged).
**Scenario notes:** B's "no wait, three" correction lands in a later turn (pattern `...|correction|after_item`), D's single-utterance corrections give `...|mid_item` (three of them flip the tagger); `confidence` exists because a config parameter can only regress a case that depends on it (low transcription confidence), so it is the case that makes the promotion gate's block real. ### D-35 · Metrics (Step 12): definitions and what is not measured (2026-09-21)
All numbers are computed from stored rows at request time; nothing is cached or hand-typed (tests recompute each independently). Stages: **stt** = end of customer speech (local check) → the independent stream's final; **gate** = call received → verdict (includes evidence waits); **repair** = hold → the re-validated commit that resolved it; **commit** = duration of the commit transaction (`t_commit_ms` now stores a duration; before it stored a clock reading); **first audio** = end of customer speech → first AUDIBLE agent audio; **barge-in** = customer speech onset → reply cut off. p50/p95 are nearest-rank on the sample (an actual observed value). **False-positive holds** are counted only over holds whose case has a validated expected state (a hold whose recorded call was actually correct); holds never judged are not counted, and the metric says so. **Final order accuracy** is n/N over ended sessions with a DECLARED intent; sessions without one are excluded, and the intent is set before the run (never derived from it). `metrics_samples` (PRD) is unused. The three pending validations mean the accuracy and false-positive numbers describe synthetic and scripted runs only.

### D-37 · Step 14: the adversarial harness, and what it found (2026-09-21)
Earlier steps proved the gate with tables, fuzzing and content matrices (tests); Step 14 makes it a harness: a corpus that TELLS LIES on purpose against the real gate, with the required outcome written next to each lie, generated into `adversarial-cases.md`. 88/88 caught, 0/15 clean calls held; it fails when the gate is deliberately broken. **Real defects it found, all fixed:** (1) the drift check was O(n²) in one sentence's length: a 190 KB reply blocked the event loop for 11 s (a prompt-injected agent could do that on purpose); now bounded (first 4,000 chars, sentences capped at 400: a documented limit, safe because speech never changes the order); (2) an unbounded customer utterance had the same cost in the extractor: now held above 20,000 characters (UNVALIDATABLE); (3) `validateGatingParams` used a plain object lookup, so `constructor`/`toString` passed as parameter names: own-key check; (4) a config version named `constructor` was accepted and used as an object key downstream: reserved names refused, and the compare table uses a null-prototype object; (5) prompts were unbounded: 100,000-character cap; (6) a non-string suite id or parent version reached the SQL binder and returned 500; (7) malformed JSON returned 500, not 400; (8) the replay seed helper could not re-seed (it reused a validation id). **Not covered:** the corpus is authored by us: it shows the gate rejects the lies we thought of, and real speech will contain phrasings the extractor has not seen.

### D-39 · Two dashboard access tiers: GUEST (no login) and OPERATOR (session-cookie login) (2026-09-22)
Owner decision, made deliberately for judge accessibility at a hackathon: a judge opening the deployed URL should see the mechanism work without asking for a credential first. **GUEST (no login, the default):** the live evidence timeline, order panel, call log and case list (read-only, including case detail and audio playback), the Metrics tab, and the ability to trigger a demo scenario playback (`POST /api/demo/:scenario`) — the one write a guest may make, since it plays prerecorded audio through the real pipeline and needs no credential to prove the mechanism. **Guest must not, and cannot:** replay a case against a config, accept a case as a regression, promote or roll back a config version, start or end a real live call, use the microphone, or create a config version — every one of those routes is gated with `requireOperator` and returns **403**, not a missing button and not 401 (401 stays reserved for a bad login attempt). **OPERATOR:** `POST /api/login` checks the SAME operator token used everywhere else (no second secret) and sets an httpOnly, `SameSite=Strict` session cookie (12 h, in-memory server-side store, cleared by `/api/logout` or a restart); the `x-tally-operator` header keeps working unchanged for scripts (`smoke:deployed`, tests). The tier is decided server-side on every request (`server/src/auth.ts`, `isOperator`/`requireOperator` in `app.ts`), independent of the UI: hiding a button is a courtesy, not the control. The dashboard shows a persistent "Guest view" / "Operator view (logged in)" banner so a judge always knows which tier they are in, and the Lab tab (config create/promote/rollback) is not shown to a guest at all (the read endpoints behind it stay guest-readable, defence in depth). **Cost:** anyone with the deployed URL can watch demo sessions and case detail (synthetic, no PII) and can run demo scenarios, which write rows to the shared database; that is accepted as the point of the guest tier, not a gap.
**Two guardrails added after a pre-deploy review (2026-09-22), before the tier ever went live:** (1) `POST /api/demo/:scenario`, the one write a guest may make, needed its own abuse limits, not just the operator gate: the scenario name is bounded to the six defined names (plus the `all` alias, which only chains them); a minimum interval between ACCEPTED starts (`demoMinIntervalMs`, default 3000 ms) returns `429 demo_rate_limited` to a client hammering the route faster than a run can genuinely finish, on top of the pre-existing "one run at a time" `409`; and finished run records are pruned after 30 minutes so the in-memory job map cannot grow without bound on a long-lived deployment. (2) Guest-readable reads (`GET /api/sessions`, `/api/sessions/:id/events`, `/api/live/:id` SSE, `/api/cases`, `/api/cases/:id`, `/api/cases/:id/audio`, `/api/cases/:id/replays`) are now filtered to `mode`/`origin_mode === 'demo'`: a session or case from a REAL live call (e.g. the pending human-mic validation, or any live test the operator runs on the deployment) is invisible to a guest — not listed, 404 by id — exactly as if the guest tier didn't exist for it. This closes a gap the original design missed: without it, any live call ever made on the deployed instance would have its audio and transcript become permanently, publicly readable the moment it produced a hold.
