## Step 9 — Safe promotion and rollback  ✅ implemented + tested (2026-09-20)

That suite is operator-accepted cases from SYNTHETIC and CAPTURED phrasing only. The real-speech validation pass (D-26) and the live-agent / live-mic validation (D-27) have NOT run. A PASS means "no KNOWN failure regressed"; it is not evidence of general reliability on real callers. The evidence tier exercises the gating parameters, not the agent prompt. The same notice is attached to every suite report and promotion response (`SUITE_VALIDATION_NOTICE`).**
- [x] **Config registry (rule 4):** versions immutable and never overwritten (`CONFIG_EXISTS`; DB triggers reject UPDATE of prompt/schema/params/parent and any DELETE); `prompt_hash` + `tool_schema_hash` verified on every load (a row that fails its hash is never trusted: suite blocks, activation refuses); the tool schema is always the contract's (a config cannot weaken hold mode); gating parameters validated (whitelist + ranges); parent defaults to the active version; append-only `config_events`
- [x] **"Run all cases" (manual trigger):** `POST /api/suite/run {config_version}` runs EVERY `regression`-tagged case through the evidence tier with the candidate's gating parameters (mandatory, deterministic, 100%). ## Known flaky tests (investigated, not silently ignored)
- [ ] 🚧 **`server/test/app.test.ts` > "WebSocket mic bridge" > "an oversize frame is refused (1009)... (1013)..."**: occasionally fails a full-suite run with `Hook timed out in 10000ms` (seen 2026-09-23, running full-suite after the real-speech P5 revert). **Investigated, not dismissed as generic CI noise**: the test's own assertions are reliable — passed 18/18 when the file was re-run in isolation immediately after the full-suite failure. Root cause identified in code, commented at both ends (`server/test/app.test.ts` near the test, `server/src/runtime.ts` in `SessionRuntime.end()`): `sendPcm()` serialises and paces every audio chunk to real time on one shared promise chain; a `ws.close(1013)` stops new frames but does not cancel frames already queued onto that chain, and `end()` awaits the full chain before returning. This test intentionally floods ~250-400 frames (up to 8 s of represented audio) before the 5 s queue bound closes the socket, so its own afterEach cleanup can need several real seconds to drain — already ~7.5 s in isolation, close enough to vitest's 10 s `hookTimeout` that added scheduler contention from ~58 other test files running concurrently can occasionally push it over. **Confirmed test-only**: a live microphone can never flood 8 s of audio in under a second, so this has no bearing on the real mic-bridge path or on gating correctness. **Not fixed**, given the deadline: a real fix would mean either shrinking the test's burst well below the 250-frame/5 s mark, or making `end()` abandon rather than fully drain the chain on an already-closed socket — both are more invasive than this pass has room for. If this file's hook-timeout recurs, re-run it in isolation first; a clean isolated pass reinforces this diagnosis rather than requiring a new one.
